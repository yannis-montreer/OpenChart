# Bar cache for the read path (after CI-5, 2026-10-17)

## Design (before the code)

CI-5 (#46) measured a 5,000-bar indicator request at 233 ms p95 (target 60) and the forming-bar tail at 44 ms (target 15), and found the bars the cause. Profiled again here (`SeriesReader.candles`, 5,000 5m bars, 30 days of synthetic minutes): 74 ms median, of which 61 ms is reading 36,000 minutes from SQLite, 3 ms aggregating, 5 ms turning the frame into records. A 2-bar tail reads 3 days of minutes: 12 ms.

- **What is cached:** per (source, instrument, timeframe, price), for the fixed timeframes built from stored M1/H1 (1m, 5m, 15m, 30m, 1h), one run of bars `[lo, hi)` exactly as `SeriesReader._from_base` computes them from the store, held as numpy arrays. A request inside the run is a slice; one that reaches past it reads only the missing part (before `lo`, after `hi`) and extends the run. **Not cached:** the tick timeframes (1s to 30s), 4h/D/W (they have their persistent cache; their forming tail stays computed), the forming M1 (folded in afterwards from the builder, as now), indicator values (CI-5's cache).
- **Version counter:** `CandleStore.epoch(source, instrument)`, bumped **before** a write is queued and **again after** it commits or fails, by one helper (`_writing`) that every candle write in the store goes through: `upsert` (the feed's closed minutes, the broker's replacement of the last 15 minutes and of the hour before a stop, the previous day's check, refill, repair, gap fill, backfill and download pages, deep H1) and `purge_instrument`; the storage step's M1 purge (task 2, another branch) bumps it too. Each bump tells the bar cache the oldest time written (`None`: everything, for purges); the cache cuts every run of that series from `bar_start(oldest - 1 h)` (writing M1 can move the hour where M1 takes over from H1) and stamps what is left with the new epoch. A run whose stamp differs from the store's epoch is never used (a write that bumped without telling the cache drops it).
- **Writes outside the store:** none in `src/` (a test fails if another module names the candle tables). Migrations and the write commands (`migrate`, `backfill`, `repair`, `purge`, `rebuild-cache`) take the data-folder lock, so they run with the server stopped; the cache is in the server's memory and starts empty.
- **A write during a read:** a read notes the epoch before it reads; it extends the run only if the epoch is unchanged afterwards (no `await` between that check and the update). Otherwise it reads the whole request from the store and returns it without caching.
- **Who uses it:** only `SeriesReader` (`/api/candles` and the indicator routes). Alerts, repair, backfill, the feed and the 4h/D/W cache read the store directly, unchanged.
- **The forming bar:** stored bars only. The live minute is folded in after the cache, per request, from `CandleBuilder.forming_m1`; the feed's closed minute is a write (epoch, cut of the last bar), so the next read rereads just that bar.
- **Size cap:** at most 50,000 bars per run (the oldest are dropped past that) and 16 MB in all (48 bytes a bar), least recently used run first.
- **Memory on a 150 MB instance:** 16 MB at most; typically 3 instruments, 2 or 3 timeframes, one price, 10,000 bars each: about 4 MB. **Open question:** CI-5's values cache is bounded at about 100 MB, too much for 150 MB.
- **Expected:** the reader's 74 ms for 5,000 bars to a few ms (a slice and a copy); `/api/candles` keeps the record and JSON work (about 10 to 20 ms); the 2-bar tail from 12 ms to about 1 ms plus the route. Whether the indicator request reaches 60 ms p95 depends on the rest of the route (worker exchange about 6 ms, digest, JSON); measured below, not assumed.
- **Tests:** two readers on one store, one with the cache, one without: equal answers (every timeframe, price, latest, pages, warmup pages back, forming fold) after every write path above, run through the real functions with the fake broker; a write during a read; every store method writing candle tables bumps before and after (statement trace); no other module writes them; the size cap; mutation check (`tools/mutate_bar_cache.py`); measured before and after with `tools/measure_values.py --bar-cache off|on`.
