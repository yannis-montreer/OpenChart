OpenChart 0.3.0 adds alerts on indicators, a safer way to remove instruments and their
data, and a fix that makes alerts crash-proof. It is still a pre-release.

**Your broker tokens stay on your own machine:** in the Windows Credential Manager, or for
the Windows service and Docker in an encrypted file in the data folder, with its key kept
apart. OpenChart sends them only to your broker (and the Telegram token only to Telegram).
Your own indicator files run in an isolated worker that has no access to them.

**Not financial advice. Use at your own risk. No warranty.** Alerts can be late or missed
(network loss, broker outages, bugs). Provided "as is" under the Apache License 2.0.

**Downloads:** `OpenChart-Server` (the server and its Windows service scripts; see the
README Quickstart) and `OpenChart-Viewer` (a desktop window for the chart). The `.exe`
files are not signed, so Windows SmartScreen warns on first launch: choose "More info",
then "Run anyway". SHA-256 sums are in `SHA256SUMS.txt`.

## What's new

- **Alerts on indicators.** Get a message when an indicator does something, not only when
  the price touches a line. Three kinds of condition:
  - an output **crosses a number** (RSI crossing down 30);
  - an output **crosses another output** (the fast average crossing the slow one);
  - a **marker or a background colour fires** (a signal from your own indicator file).
- **Closed bars only.** An indicator alert is checked when a bar has closed, never while it
  is still forming. So a signal arrives after the bar closes, not during it, and it is
  decided on values that cannot change. Alerts on indicators start at the 1-minute
  timeframe; a chart on seconds uses 1 minute for them.
- **Where you manage them.** One dialog creates and edits all three kinds. It opens from
  the bell on an indicator's legend row, or from the Alerts panel's `+`. The panel shows
  each alert's state (armed, stopped with its reason, error, triggered, expired) and the
  warnings on it.
- **Warnings.** An alert on a file that looks ahead at bars that do not exist yet still
  works, with a visible warning that a catch-up after an outage may differ from what you
  saw live. An alert that is behind (two bars or more) says so.
- **Alerts stop when their indicator goes.** Remove the indicator from the chart, or edit
  the file so it no longer has the output, and the alert is stopped, not deleted. It keeps
  its settings and the panel shows the reason. Editing a file or the parameters of an
  indicator re-arms its alerts: the first check after the edit records the state and
  never fires.
- **A fire and the alert's state are written in one step.** A crash or a power cut in the
  middle can no longer fire an alert twice or lose a fire. This applies to the alerts on
  lines too, not only to the new ones.
- **Removed instruments** appear in their own **Removed** section in Settings, hidden from
  the chart. **Add back** brings one back with its history. A separate **Delete data…**
  action frees the space: it shows a preview of what will go and asks you to type a
  confirmation first. It also deletes the chart's indicators of that instrument.
- **Layouts keep your indicator alerts armed.** Applying a layout that would stop any
  alert asks first and names them. Nothing stopping, no question.
- **Deleting an indicator definition or an instrument counts and names its alerts first,**
  so nothing stops without you seeing it.
- **The built-in indicators are checked against independent reference implementations**
  (plain loops written from each indicator's definition), **not against another charting
  platform's output.** Small differences from another platform are possible.
- Smaller fixes: a test that depended on the second of the minute, a hang when the alert
  dispatcher was drained, and a pinned `aiosqlite` version with a test that guards the call
  the atomic write depends on.

## Known limits

- **OANDA only,** and one server per OANDA account (about two price streams per practice
  account).
- **Indicator alerts are evaluated on closed bars,** so they are never instant: expect
  them up to a bar late. Not on seconds timeframes. No alerts on an indicator from another
  timeframe (those indicators do not exist yet).
- **A replay after an outage is one computation.** For a file flagged as looking ahead,
  a catch-up can differ from what you would have seen live. The catch-up covers at most
  7 days, as for line alerts.
- **A bar the broker later replaces** never cancels an alert already sent. When the
  broker's candle contradicts it, the alert's log records both values.
- **Drawings:** alerts work on the horizontal line, trendline, ray and extended line only,
  not on the newer drawing tools.
- **Custom indicator code is code:** treat a file like a program you run. On a source
  install it can read your files and use the network. The browser editor is off on a source
  install, by design.
- **Retention deletes data.** The defaults (30 days of ticks, 2 years of minutes) apply
  as in 0.2.0.
- **Not included:** 5-second candles, bar replay, backtesting, a Linux service script (use
  Docker), automatic updates. The Docker image is not published: build it from the
  repository. Some README screenshots predate this release.
- **The phone is for reading the chart;** drawing works best with a mouse.

## Updating from 0.2.0

**Before updating, back up the data folder.** The first start of 0.3.0 upgrades the
database, and 0.2.0 cannot read it afterwards. Going back means restoring the backup
together with 0.2.0.

**What the first start does.** It applies two small migrations, in order, since 0.2.0:

| Migration | What |
|---|---|
| 0010 `indicator_alerts` | new columns for the reason an alert stopped and for the bar, value and correction of an indicator alert's fire, and a rule of one fire per alert and bar |
| 0011 `indicator_alert_evaluation` | new columns recording what each fire was decided on |

0011 is the newest migration in this release; nothing comes after it. Neither rewrites
your candles; both add columns and an index, and your existing alerts and their logs stay
as they are. The log shows each as `database migration 00NN ... applied`, with its time.
If a migration cannot finish, it changes nothing and the log says why.

**Windows service (release zip):**
1. Back up: `openchart.exe backup --data-dir C:\ProgramData\OpenChart\data`.
2. Extract the new server zip to a new folder and run its `install-service.cmd`. It stops
   the running service, upgrades the database, points the service at the new version and
   starts it. Your data, settings and tokens stay.
3. Check `C:\ProgramData\OpenChart\data\logs\service.log`: it shows migrations 0010 and
   0011 applied and the feed connecting. Then delete the old folder.

**From a source checkout:**
1. Stop the server.
2. Copy the data folder.
3. `git pull` (or check out the `v0.3.0` tag), then `pip install -e .`: this release pins
   `aiosqlite`.
4. Run `openchart migrate`.
5. Compare `openchart stats` before and after: the counts must be equal.
6. Start the server.

**Docker:**
1. Back up: `docker compose exec openchart openchart backup`.
2. Then `docker compose build` and `docker compose up -d`. The upgrade runs at start.
