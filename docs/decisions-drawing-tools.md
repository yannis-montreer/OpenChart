# Decisions: more drawing tools (vertical line, rectangle, channel, Fibonacci, text, measure)

2026-10-17. Alerts on the new tools are **not** built; "Alerts later" records what each would need.

**Shared.** Same `drawings` table (`type` is free text), routes, `drawing_changed` broadcast and per-instrument list: **no migration**. Anchors stay `{t, p}` (UTC seconds, price). New `type`s: `vline` (1 anchor), `text` (1), `rect` (2), `fib` (2), `measure` (2), `channel` (3). The server checks the anchor count and the shape rules in `drawing_rules.py`; `shapes.ts` has the same rules; one fixture (`shape-rules.fixture.json`) is run by both. Style gains two optional keys, stored only when set: `fill` (int 0-100, opacity %) and `extend` (bool). `color`, `width` 1-4 and `dash` stay. Alerts: `POST /api/alerts` refuses a `line_cross` on the new types until they are built (the engine would raise on an unknown type). All pure geometry is in `shapes.ts` (tested); the controller only paints and handles the mouse.

**Placement (all).** Click-click or press-drag-release (a channel: the drag places P1-P2, a third click places P3), Ctrl magnet on every anchor, Esc cancels, tool returns to the cursor, right-click menu, style toolbar, Del, clone, hidden with the eye, moves as a whole by dragging the body (shifted in bars and price, as the ray).

**vline.** Anchor: `t` used; `p` = click price, kept only so the shape is a normal point (never drawn, no price label). Full pane height at the slot of `t` (future slots too). Moves in time only. Style: color, width, dash, label (top). No slope. *Alerts later:* a time alert (fires once at `t`), new alert type, no price.

**rect.** Two opposite corners in any order; valid with trading time between them and different prices. Four corner handles (a corner takes its `t` from one anchor and its `p` from the other). Filled box plus border. Style: color, width, dash, fill (default 15), label (inside, top left). No slope. *Alerts later:* an `enters`/`leaves` condition (type `zone`): inside = price in [lo, hi] and time in [t_min, t_max]; leaves after t_max never fires, the alert expires there. Needs the previous side stored in the alert state.

**channel.** P1-P2 is the base segment (a trendline). P3 sets the offset `d = p3 - base_extended(t3)`; the second line is the base moved by `d`, so it is parallel **in trading time** (SPEC section 9), the same distance in price at every moment, across weekends and breaks. Valid with trading time between P1 and P2 and `d != 0`. Dragging P1 or P2 keeps `d` (P3 follows); dragging P3 sets `d`. Style: color, width, dash, fill (between the lines, default 10), extend (`false` segment, `true` rays to the right), label. *Alerts later:* two `line_cross` alerts, `line` 0 or 1, from `channel_lines(points, clock)` in `alerts/geometry.py` (the two lines as ordinary `(kind, points)` pairs); moving the drawing re-arms both.

**fib.** A = start (level 1), B = end (level 0): `price(l) = B + (A - B) * l`, levels 0, 0.236, 0.382, 0.5, 0.618, 0.786, 1 (fixed in v1; custom levels would be `style.levels`). Valid with trading time between A and B and `A.p != B.p`. Horizontal segments from `min(t)` to `max(t)` (to the pane edge with `extend`), each labelled "level (price)", plus a thin diagonal A-B. Style: color, width, dash, extend. Levels are flat, so the trading clock only places the ends. *Alerts later:* `level_cross` with `{drawing_id, fib_level}`: the level price is recomputed when the drawing moves (re-arm, as for a line).

**text.** One anchor; the text is `label` (required, 1-100 characters; `clear_label` is refused on a text). Drawn left-aligned above the anchor. Size from `width` (1-4 = 12, 14, 18, 24 px), color. Asked for right after the click; "Edit text…" in the menu. *Alerts later:* none (a note).

**measure.** Two anchors, from and to; valid when they differ in trading time or price. Straight segment with an arrow and a box: change in price and pips, percent, bars (on the timeframe shown, from the chart's time index) and wall-clock duration. Stored and synced like the others (deleted by the user, not on click-away). Style: color (up/down tint is not used, one colour), width, dash. No label. *Alerts later:* none.

**Tests.** Rules and geometry first (pytest, vitest, fixture), then `tools/mutate_drawing_tools.py` breaks one rule at a time and the tests must fail.

**Taken while building.** Shortcuts Alt+V (vertical), B (box), C (channel), F (Fibonacci), M (measure), X (text); Alt+R stays "reset view". The default fill (15 rectangle, 10 channel) is applied when painting, so a drawing without `fill` follows the default. A rectangle is clickable inside only while it has a fill; otherwise on its edges. A drag recomputes from the anchors as they were at the press, so a move the rules refuse can be undone by moving back. A channel anchor off the base line cannot be placed at once on it (the click is ignored). Tool buttons for the new tools sit below the line tools; the Alt+A key and the Alert button on a selected new tool say that alerts are not available yet.

**Separate from the drawing tools: 405 or 404 (PR #48, item 1).** With a built frontend, a `DELETE` or `POST` on a path no route matches (an id with an encoded slash, `..%2Fmine`) was answered `405` by the static mount; without a build, `404`. A real install always has the frontend built, and the path does not exist for any method, so `404` is right: `WebFiles` (`api/app.py`) answers `404` to any method but GET and HEAD. One test (`test_api.py`) runs both setups and requires the same answers.

**Drawings management (PR #48, item 2).** `locked` and `hidden` are two more optional boolean style keys (strict booleans, stored only when sent). The server stores the lock but does not enforce it: the chart will not move or delete a locked drawing (no drag, no handles, Del and the menu refuse; "Delete all" skips it), a script or an undo still can, and the list panel's delete is disabled while locked (unlock first; the safest reading). Hidden drawings are neither painted nor hit; the eye in the toolbar column still hides all at once, per browser. Undo/redo (Ctrl+Z, Ctrl+Shift+Z or Ctrl+Y, the two buttons) keeps up to 100 steps in memory, cleared on an instrument switch or reload. Each step is an ordinary API call: create, delete (a drawing comes back under a new id, so the stack renames it), or a patch with the old values; "Delete all", "Hide all" and "Lock all" are one step. A failed undo clears the stack (it no longer matches the server). A clone is neither locked nor hidden.

**Alerts on the new tools: what the engine would need (nothing is built).** Today an alert follows one price line: `line_value(alert, t)` is `line_price(drawing.type, points, t, clock)` and a crossing is two observations on different sides. Recommended order, smallest first:
1. **Fibonacci levels.** Each level is a horizontal line at `B.p + (A.p - B.p) * level`: a new nullable `fib_level` on the alert (a migration, numbered at merge time) and one more branch in `line_value`; no new state. One alert per level (the dialog offers the seven as checkboxes). Moving the drawing changes the price, and `drawing_changed` already re-arms on changed points. Decide whether a level lives after `max(t)`: recommended yes (like an `hline`), the chart shows it to the edge only with `extend`, so the bell should say so. Risk: the names ("Fib 0.618"), the Telegram text and the alerts panel know only lines and levels.
2. **Channel.** Two lines: `channel_lines(points, clock)` in `alerts/geometry.py` returns two `(kind, points)` pairs (`trendline`, or `ray` with `style.extend`; the second is the base moved by `channel_offset`), and the alert gets a nullable `line_index` (0 or 1, a migration). `line_value` then calls the existing `line_price`, so segment ends, rays and `None` outside the line behave as for a trendline. Risk: the offset is measured on the trading clock, so a closure learned later moves the second line a little (on the chart and for the alert alike, both use the same function); a test must pin both to one clock.
3. **Rectangle, enters or leaves.** New type `zone` with a nullable `zone_event` (`enters` or `leaves`, a migration) and new engine state: the last observation was inside or outside (`AlertState`, persisted like the last side of a line). Inside means `t0 <= t <= t1` and `lo <= price <= hi` (time compared as plain UTC seconds: ticks only exist while the market is open and the trading clock is monotonic, so it adds nothing but anchors inside a closure, which the rules already refuse as corners). The time extent decides when the alert lives: it arms only after an observation inside the time window, fires `enters` on outside to inside, `leaves` on inside to outside, and expires silently at `t1` (running out of time is not leaving; a rectangle that ends over a weekend ends at its edge, not at the next tick). A rectangle starting in the future must not fire `enters` at `t0` for a price already inside (no fresh observation), as for lines. Risks: catch-up after sleep (`candle_close` is simple, `touch` needs a rule for a candle that spans the band: recommended the candle's close and the previous close decide, so a wick alone never fires), the dialog, and the wording in the notification.
4. **Vertical line** is not a price alert: a time alert (`time`, fires once at `t`, needs the watchdog's clock, not the tick stream). Last, and separate.
Common risks: migrations clash with other open PRs (take the next free number at merge); the bell and the menu entry (hidden today for the new tools) come back type by type; every step needs engine tests on the fixed clock (`tests/clock.py`) around the breaks, and the mutation tool extended for the new rules.
